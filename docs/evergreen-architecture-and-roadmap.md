# 如意鲜果蛋糕长期架构与产品路线

## 使命

让更多人用 AI 低门槛设计自己的蛋糕图，在游戏化互动中获得高级价值感，并把优秀设计连接到本地蛋糕师生产，形成“创作 -> 分享 -> 需求 -> 报价 -> 制作/配送”的商业闭环。

## 核心判断

AI 绘画引擎、模型、供应商和提示词技巧会快速变化；长期不变的是领域对象、状态机、审计边界、用户价值循环和商家履约接口。因此系统要把“变化”限制在 provider、prompt template、运营策略和 UI 活动层，把“稳定内核”沉到领域模型和 API 合约里。

## 三条主线

### 版本方向

1. 玩法增长优先：先验证用户是否愿意用 AI 画蛋糕、接任务、微调、发布和互动。这是 v0.3 的主方向，也是冷启动内容池的前提。
2. 传播裂变优先：再验证作品能否通过分享、投票、玫瑰、做同款和榜单带来新用户。这是 v0.4 的主方向，也是低成本获客的前提。
3. 交易转化优先：最后强化需求发布、附近蛋糕师报价、订单履约、支付和售后。这是 v0.5 之后的主方向，也是商业化闭环的前提。

### 主闭环

1. 任务创作闭环：`DesignTask -> CakeWork -> BotReview -> Vote/Rose -> InspirationCoupon`。
2. 作品传播闭环：`CakeWork -> ShareLanding -> FriendVote/Rose -> WorkRanking -> AdoptSameStyle`。
3. 制作交易闭环：`CakeWork -> Demand -> Quote -> OrderIntent/Order -> Fulfillment -> Review/AfterSale`。

三条闭环共用同一个作品对象，不能拆成三套互不关联的功能。作品既是游戏化创作结果，也是传播素材，也是制作需求的起点。

## 理论支撑

- 信息论：用户输入的信息量有限，系统要通过结构化字段、任务、道具、风格选项和微调反馈降低歧义，提高有效信号密度。
- 熵与复杂系统：AI 输出、用户互动和商家履约都会增加不确定性。系统通过审核、状态机、版本化 prompt、日志和指标看板降低业务熵。
- 控制工程：把产品看成反馈控制系统。输入是用户想法，控制器是 prompt/任务/审核/推荐，输出是设计图和订单线索，反馈是投票、玫瑰、采用、报价、成交。
- 软件工程：稳定接口、清晰模块边界、版本化配置和自动化验证优先于一次性功能堆叠。
- 计算机科学：用抽象数据类型和有限状态机定义作品、需求、报价、订单、审核，不让页面直接决定业务真相。
- 群论/对称性：玩家、AI Bot、蛋糕师、运营后台在不同视角下操作同一个作品对象；保持对象身份和状态变换一致，降低多端重复逻辑。
- 博弈论与机制设计：奖励、投票、报价会改变用户行为，必须防刷、限次、审核、延迟发放，避免激励劣化内容质量。
- 排队论：审核队列、报价队列、制作排期和客服投诉都应被视为队列，后续要看等待时间、处理率和积压量。
- 人机交互：第一屏必须让用户立刻开始玩；商业化和规则放在订单、我的、后台中承接。
- 领域驱动设计：核心语言保持稳定：作品、任务、灵感券、玫瑰、需求、报价、蛋糕师、配送、售后、审核。

## 稳定内核

### 领域对象

- `CakeWork`：AI 蛋糕作品。核心字段：用户、标题、prompt、图片、场景、风格、尺寸、预算、公开状态、审核状态、互动数。
- `DesignTask`：每日/活动任务。核心字段：主题、目标人群、风格约束、奖励规则、有效期、完成条件。
- `Demand`：制作需求。核心字段：作品、期望日期、预算、人数、口味、地址、联系方式、是否允许调整、审核状态、报价状态。
- `Baker`：蛋糕师/蛋糕店。核心字段：资质、服务范围、起订价、擅长品类、审核状态。
- `Quote`：报价。核心字段：蛋糕价格、配送费、制作周期、可制作日期、还原说明、状态。
- `OrderIntent`：报价意向/订单意向。第一阶段不等同真实支付订单，后续可升级为微信支付订单。
- `Order`：用户确认报价后的可恢复订单。核心字段：用户、需求、报价、蛋糕师、金额、履约状态、配送/自提信息、售后状态。
- `Fulfillment`：制作履约记录。核心字段：商家确认、制作中、出餐、配送/自提、完成、异常。
- `ModerationCase`：审核案件。统一承接作品、需求、商家资质、售后、灵感券。
- `Generation`：生图记录。核心字段：作品、provider、model、size、promptVersion、promptProfile、输入快照、输出 URL、失败原因、耗时。

### 状态机

- 作品：`private -> public_pending -> public_approved -> public_rejected`。
- 需求：`reviewing -> quoting -> selected -> closed`。
- 蛋糕师：`pending -> approved -> rejected -> suspended`。
- 报价：`active -> selected -> cancelled`。
- 订单意向：`intent_confirmed -> merchant_confirmed -> producing -> delivering -> completed -> disputed`。
- 支付订单：仅在微信支付接入后启用，不能替代订单意向状态机。
- 订单履约：`created -> baker_confirmed -> producing -> ready -> delivering_or_pickup -> completed -> disputed`。

### 稳定 API 合约

- `POST /works/generate`：输入结构化设计意图，返回作品和 generation 元信息。
- `PATCH /works/:id/publish`：提交论坛审核，不直接公开。
- `POST /demands`：发布制作需求，默认待审核。
- `PATCH /admin/*/review`：后台审核统一入口。
- `POST /quotes`：蛋糕师报价，只允许审核通过的需求和蛋糕师。
- `PATCH /quotes/:id/select`：用户选择报价。
- `POST /payments`：支付占位或真实支付创建。前端可先用 `intent` 模式。

## 当前技术债真实性判断

- JSON 文件存储：真实 P0 风险。体验版可用，真实并发、交易、审计、图片规模上来后必须迁移数据库。
- H5/后端/小程序类型重复：真实 P1 风险。短期可接受，长期应用共享 schema 或 OpenAPI 生成类型。
- 支付 provider 浅抽象：真实 P0 风险。`PAY_PROVIDER=wechat` 不能只改字段，真钱前必须补 JSAPI 下单、回调验签、幂等、退款和订单状态机。
- 审核入口分散：真实 P1 风险。已移除公开需求审核绕过入口；后续仍应统一为 `ModerationCase`，避免更多审核逻辑分散。
- `ADMIN_PASSWORD` 未设置时后台放行：本地开发是便利，公网部署是 P0 风险。正式环境必须 fail closed 或至少部署检查强制配置。
- 资质上传公开暴露：真实 P1 风险。已取消 `/uploads/` 静态公开，当前只返回 `upload://id` 私有引用；正式版需要后台鉴权下载和对象存储。
- 缺真实身份与角色边界：真实 P0 风险已部分收口。当前已补服务端 session token 骨架，生产环境写接口不再信任无 token 的 body/query `userId`；但真实微信登录还需要你提供 AppSecret 后才能完成真机验证。
- 缺可恢复订单实体：真实 P0 风险。当前小程序主要用当前会话对象拼订单页；后续必须后端持久化 `Order` 和履约状态。
- 分享传播链路不完整：真实 P0 产品缺口。当前可分享，但缺作品落地页携带 id、好友投票/采用/发起同款需求。
- 任务/奖励文案进入生图 prompt：局部问题。短期帮助游戏感，长期应把“创作意图”和“运营奖励元数据”分离，避免污染生图质量和审核语义。

## 易变外壳

- AI provider：千问、火山、中转、未来模型都应只替换 provider adapter。
- Prompt template：必须版本化，不能散落在页面或 provider 内部。
- 玩法活动：每日任务、灵感券倍率、榜单规则属于运营配置。
- UI 风格：可高频迭代，但不能改变领域对象语义。
- 支付策略：第一阶段报价意向，第二阶段微信支付，第三阶段担保交易/结算。
- 商家履约：先人工联系，后门店自配送，再接第三方配送或地图轨迹。

## Prompt 策略

结论：不要把完整 system prompt 写死在业务函数里。应当“稳定规则版本化 + 用户输入结构化 + provider 适配层转换”。

当前代码已增加 `apps/api/src/ai/prompt-template.ts`：

- 固定 `PROMPT_VERSION`，便于回溯每张图由哪个规则生成。
- 支持 `AI_PROMPT_PROFILE`，默认 `social-game`，也可切到 `production`。
- 输出 `prompt` 和 `negativePrompt`，provider 根据能力使用。
- 返回 `promptVersion` 和 `promptProfile`，后续可进入作品/generation 记录。

后续建议：

- 增加 `Generation` 表，记录 provider、model、promptVersion、seed、输入字段、输出 URL、失败原因。
- 把玩法任务中的奖励、灵感券、积分等运营元数据从生图 prompt 中剥离，只保留主题、场景、风格、颜色、尺寸、预算和制作约束。
- 增加 prompt A/B 测试，不直接覆盖旧版本。
- 不允许前端传完整 system prompt，只允许传结构化字段和用户自然语言想法。

## 产品阶段

### 阶段 1：审核版 MVP

- 核心：生成、微调、发布作品审核、发布需求审核、蛋糕师报价、确认报价意向。
- 支付：不展示虚拟支付，使用报价意向确认。
- 增长：每日任务、AI Bot 点评、投票、玫瑰、做同款。
- 目标指标：生成率、微调率、提交审核率、需求发布率、报价率、联系方式留存率。

### 阶段 2：真实试运营

- 接真实登录、手机号、HTTPS 域名、阿里百炼千问真实生图。
- 长治 10 到 30 个蛋糕师入驻。
- 后台人工审核作品、需求、资质和投诉。
- 线下确认成交，收集制作成品反馈。
- 增加“我的作品/我的需求/我的报价/我的订单”后端列表，支持换设备恢复。
- 增加作品分享落地页：好友打开后可投票、送玫瑰、采用同款或发布同款需求。
- 补齐作品传播闭环：分享卡片、作品详情、好友投票、榜单、做同款回流和任务参与回流。

### 阶段 3：交易闭环

- 接微信支付、支付回调、退款、售后证据。
- 订单意向升级为订单履约状态机。
- 增加商家排期、报价 SLA、配送状态。
- 增加商家确认制作、制作中、出餐、配送/自提、完成、异常处理。
- 补齐制作交易闭环：需求审核、报价对比、选择师傅、订单恢复、履约节点、评价和售后工单。

### 阶段 4：规模化平台

- 数据库迁移到 PostgreSQL，文件迁移对象存储。
- 接内容安全接口和风控规则。
- 城市扩张、商家等级、推荐算法、任务系统后台化。

## 近期工程路线

1. 补 `Generation` 数据模型和持久化，记录 prompt 版本、provider 和模型。
2. 补 `Order` 和 `Fulfillment`，让确认报价后的订单可恢复、可列表、可履约。
3. 用真实微信 AppSecret 验证 session token 链路，并继续把后台、订单、履约的角色权限细化到账号/角色级别。
4. 补作品分享落地页和历史列表：我的作品、我的需求、我的报价、我的订单。
5. 抽 `ModerationCase`，让作品、需求、商家资质、售后、灵感券统一进入审核队列。
6. 引入共享接口 schema，减少后端、H5、小程序类型漂移。
7. 正式部署前强制 `ADMIN_PASSWORD`，公网后台不能默认放行。
8. 数据库迁移到 PostgreSQL 或至少 SQLite，上传文件迁移对象存储。
9. 真实支付前实现订单状态机、微信支付回调验签、幂等和退款。

## 维护原则

- 所有外部 provider 都通过 adapter 接入，不让页面直接依赖模型字段。
- 所有用户公开内容都先落审核状态，不让生成即公开。
- 所有奖励都先进入审核记录，不自动承诺现金。
- 所有关键状态变更都要有 audit log。
- 每次上新功能必须回答：它改变了哪个领域对象、哪个状态机、哪个指标。
